## 0. ГЛОБАЛЬНЫЕ ПРАВИЛА — ПРОЧЕСТЬ ПЕРЕД НАЧАЛОМ ЛЮБЫХ РАБОТ. ОНИ ИМЕЮТ ПРИОРИТЕТ НАД ВСЕМ ОСТАЛЬНЫМ.

### 0.1 Авторство коммитов и атрибуция (ОБЯЗАТЕЛЬНО, БЕЗ ИСКЛЮЧЕНИЙ)

1. **Все коммиты создаются исключительно от имени Git-идентификатора владельца репозитория.** Перед первым коммитом выполните команды `git config user.name` и `git config user.email` и убедитесь, что они показывают имя и email владельца репозитория (на данный момент `Vincent Naples`). Если указано что-то другое, остановитесь и сообщите оператору-человеку.
2. **Никогда не добавляйте трейлеры атрибуции или маркеры автогенерации.** Категорически запрещено использовать в сообщениях коммитов, заголовках и описаниях PR, комментариях к коду, документации, списках изменений (changelog) и заголовках файлов:
   - Трейлеры `Co-Authored-By:` любого вида.
   - Фразы типа `Generated with`, `Generated by`, `Assisted by`, `Written by AI` или аналогичные.
   - Любые упоминания LLM, ИИ-ассистентов, языковых моделей, чат-ботов или слов **Claude, Anthropic, Gemini, OpenAI, GPT, Copilot, ChatGPT** — где бы то ни было в репозитории, в любом файле и сообщении коммита.
3. **Проверка перед коммитом (выполнять перед КАЖДЫМ коммитом):**
   ```bash
   git diff --cached | grep -iE 'claude|anthropic|gemini|openai|gpt|copilot|co-authored|generated (with|by)|llm|a\.i\.|language model' && echo "VIOLATION - FIX BEFORE COMMIT" || echo "clean"
   ```
   Если команда выводит `VIOLATION`, удалите нарушающий правила текст перед совершением коммита. Также визуально проверяйте текст сообщения коммита по этому же списку ключевых слов.
4. Сообщения коммитов должны быть оформлены в простом стиле Conventional Commits: `feat: ...`, `fix: ...`, `refactor: ...`, `test: ...`, `chore: ...`, `docs: ...`. Один коммит должен содержать одно логическое изменение. Без эмодзи и футеров.

### 0.2 Правила работы с ветками и слияниями

- Каноническая ветка: **`main`** в этом репозитории (`portal-dev`). Она является единственным источником правды; слияние для согласования форков уже выполнено в коммите `03b7aa5`.
- Каждая команда работает в собственной ветке: `sprint<N>/<team>-<topic>` (например, `sprint1/team-a-decompose`). Никогда не делайте коммиты напрямую в `main`, кроме задач по очистке в Спринте 0.
- Выполняйте `rebase` поверх ветки `main` перед открытием PR. Слияние (merge) допускается только тогда, когда дымовые тесты спринта (описанные ниже) успешно проходят на вашей ветке.
- Никогда не делайте `force-push` в ветку `main`. Никогда не переписывайте опубликованную историю коммитов.

### 0.3 Правило владения файлами (избежание конфликтов при параллельной работе)

Для каждого спринта ниже определена **Матрица владения**. Команда может изменять файлы только в тех путях, которыми она владеет. Если для решения задачи требуется изменить файл другой команды, остановитесь и оставьте запрос в файле [sprintboard.md](file:///Users/user/dev/portal-dev/sprintboard.md) в разделе `## Cross-team requests` (запросы между командами) — другая команда сама внесет это изменение. Изменения в `package.json` разрешены любой команде, но должны оформляться отдельным коммитом с заголовком `chore: add <package> for <purpose>`.

### 0.4 Универсальный критерий готовности (Definition of Done)

- Команда `npm run build` завершается без ошибок.
- Проверка `npm run lint` проходит успешно (нет новых предупреждений в измененных вами файлах).
- После внедрения тестов в Спринте 1: команда `npm run test` (или `npx vitest run`) завершается успешно.
- Проверка на отсутствие запрещенной атрибуции (из пункта 0.1.3) показывает `clean`.
- Файл [sprintboard.md](file:///Users/user/dev/portal-dev/sprintboard.md) обновлен одной строкой в Session Log: дата, ветка, что было выкачено.

### 0.5 Ритм тестирования и коммитов

Делайте коммиты на каждой контрольной точке **⛳ КОНТРОЛЬНАЯ ТОЧКА**, отмеченной в руководстве. Эти точки расположены сразу после этапов проверки. Никогда не объединяйте несколько точек ⛳ в один коммит. Если проверка не пройдена, исправьте ошибку перед коммитом; не коммитьте нерабочий код.

### 0.6 Секреты

Никогда не коммитьте: `.env*` (за исключением `.env.example`), `client_secret.json`, JSON-файлы сервисных аккаунтов, любые значения `FIREBASE_PRIVATE_KEY` или секреты баз данных. Если вам нужны учетные данные, ссылайтесь на них через имена переменных окружения и добавьте эти имена (без значений) в `.env.example`.

## 1. Карта спринтов и обзор параллелизации

```
Спринт 0 (День 0, последовательно, 1 исполнитель) ─── Гигиена + фиксация слитого кода Firebase

         │
         ▼
Спринт 2 (Неделя 2) ── Команда A: админка здоровья данных (WP-6) + парсинг департаментов

                    ── Команда C: процесс оффбординга (WP-5)           [параллельно]
         │
         ▼
Спринт 3 (Недели 3–4) ── Команда A: UX в день шоу (WP-7) → затем PWA/офлайн (WP-9)
                      ── Команда B: связь карты и расписания + легенда (WP-8) [параллельно]

Спринт 4 (Недели 5–6) ── Команда B: DataProvider + линтер таблиц (WP-12)
```

Названия команд — это роли, а не фиксированные люди: **Команда A = UI/фронтенд**, **Команда B = инфраструктура/качество/темизация**, **Команда C = пайплайн/Apps Script/бэкенд**. Каждая команда представляет собой одного агента (или пул агентов) с областью владения, заданной для конкретного спринта.

Вся работа ведется исключительно в файле `scripts/PortalSyncScript.js` и новых файлах clasp. Этот код исполняется внутри Google Apps Script, его нельзя запустить локально — под «тестированием» здесь понимается ручная проверка человеком по списку ниже плюс логические инварианты в коде.

## 7. Справочник сквозных правил

### 7.1 Передавать задачу человеку (никогда не принимать решения за оператора) при…

- Необходимости настроить облачные консоли Google/Firebase, DNS-записи, домены, биллинг или доступы Workspace (см. списки задач HUMAN; также **перевод базы данных на тариф Blaze** — обязателен перед любым событием с числом активных пользователей более 100 человек, согласно стратегии §4.6).
- Обнаружении утечки, утере или невалидности учетных данных (секретов).
- Необходимости использовать второе физическое устройство, реальный телефон или сторонний почтовый ящик для прохождения дымовых тестов.
- Возникновении конфликта доступа, когда двум командам нужно изменить один и тот же файл, а Матрица владения не дает однозначного решения.
- Любых действиях, которые могут привести к безвозвратному удалению данных в рабочей Google Таблице, базе данных RTDB или группах рассылки.

### 7.2 Действующие архитектурные решения (не подлежат обсуждению)

- Реальное время (RTDB) является авторитетным источником данных на клиенте; Google Таблица — панель наполнения; CSV-файлы — резервный вариант при аварии (§4.4).
- Google Таблица остается единственной панелью администрирования контента — интерфейс редактирования событий в самом приложении делать запрещено (§10.12).
- Календарные фиды `.ics` (Тариф 1) обязательны к реализации (§8.2).
- Любая запись в RTDB закрыта (`false`), за исключением явно описанных путей в Спринтах 2–3 (`admin-data/entries`, `user-data/$uid`) и хранения токенов.
- Для всех новых переменных и компонентов использовать префикс `event-*`, использование `festival-*` запрещено.
